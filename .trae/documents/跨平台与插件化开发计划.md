## 1. 目标与范围

本计划围绕三个方向展开：

1. **可复制运行环境**：用虚拟环境、锁定依赖和跨平台启动脚本，让新机器可以稳定复现同一套运行环境。
2. **跨平台适配**：以 Windows 现有能力为基准，优先补齐 Linux 的基础指标；温度、独显、核显、物理盘型号等能力按平台可用性降级。
3. **插件化集成**：提供通用嵌入组件，在 DSH（DeepSeek Harness）、Trae、Cursor、Codex 等编程平台中显示完整页面，并在对话区域左上角提供可折叠的缩略监控。

不在本次范围：

- macOS 的完整硬件适配（只保证基础 psutil 指标和可启动）。
- 历史数据持久化、告警、云端同步。
- 向 VS Code Marketplace 或各平台应用商店正式发布。
- 修改 Windows 内核驱动或自研温度驱动。

验收总目标：

- 全新机器执行一条初始化命令即可创建 `.venv` 并安装可复现依赖。
- Windows 10/11 行为与当前版本保持一致；Ubuntu 22.04/24.04 可启动并稳定提供基础指标。
- 编程平台中可打开 `/plugin` 集成页，并通过嵌入脚本或适配器在对话区左上角显示缩略监控。

### 1.1 优先级与取舍

| 优先级 | 内容 | 判断依据 |
|---|---|---|
| Must | 虚拟环境、依赖锁定、跨平台启动脚本、Windows 行为不回退 | 没有可复制环境，后续跨平台和插件都无法稳定验证 |
| Should | Linux 基础指标、平台能力表、前端的平台降级 | 用户明确要求适配大多数设备，但不需要一次性对齐全部 Windows 专有指标 |
| Should | 通用嵌入组件、`/plugin` 集成页、左上角缩略监控 | 用户明确选择的插件形态 |
| Could | VS Code/Trae/Cursor 扩展、Codex 状态行、DSH 配置模板 | 依赖各宿主能力，先提供薄适配器，避免承诺不可实现的聊天 DOM 注入 |
| Won't（本期） | macOS 完整适配、历史数据、告警、应用商店发布、自研驱动 | 与当前目标无直接关系，避免范围膨胀 |

### 2.3 可复用的跨平台部分

以下逻辑可以保持在共享层，不需要按平台重写：

- 快照与错误隔离：`put`、`put_error`、`collect`（L91-111）。
- CPU、内存、网络速率差分、系统信息、进程排行（L115-147、L284-313、L603-658）。
- 分区用量和网卡 psutil 回退（L264-278、L729-749）。
- NVML 封装 `NvmlSession`（L151-212），Linux 有 NVIDIA 驱动时同样可用。
- 采样调度 `sampler_loop`（L1154-1217）只通过 `collect()` 取数，可改为平台采集器注册表。
- Flask 鉴权、CORS、页面服务、快照读取（L1220-1281）。

### 2.4 前端与嵌入相关现状

- `API_BASE` 硬编码为 `http://${location.hostname}:${location.port || 5678}`（主页面 L551，桌面版 L527），在 HTTPS 页面、反向代理、远程开发场景下会失败。
- 主题引导、主题切换、轮询、侧栏都直接依赖页面 DOM；现有页面包含固定定位侧栏，不适合直接塞进小尺寸缩略窗。
- 温度标签包含 `CPU PKG/OHM/ACPI/WMI` 等 Windows 语义；网卡侧栏使用 `ipconfig` 文案。
- 页面通过 Google Fonts 加载字体，在 WebView/CSP 环境下可能被拦截（正文会回退系统字体）。
- 服务端未设置 `X-Frame-Options` 或 `frame-ancestors`，默认可被任意站点 iframe 嵌入，需要显式限制。

### 2.5 嵌入平台约束

| 宿主 | 能否注入对话区左上角 | 可行方案 |
|---|---|---|
| DSH / DeepSeek 网页 / Codex Web | 取决于宿主 DOM，通常可以 | `embed.js` + 可配置 `data-target`，或用户脚本 |
| Trae / Cursor / VS Code | 内置聊天 DOM 没有公开注入 API | 扩展侧边栏 WebviewView、独立面板、状态栏；不要承诺注入聊天 DOM |
| Codex CLI | 无对话框 | 终端状态行脚本或独立页面 |

其他约束：

- HTTPS 页面嵌入 `http://127.0.0.1` 时，Chrome/Edge 对 loopback 有豁免，Safari/iOS 会拦截混合内容。稳妥方案是用户脚本/扩展在宿主上下文中取数并直接渲染，不使用 iframe。
- VS Code 系 Webview 是沙箱 iframe，需要扩展提供 CSP；远程/Codespaces 下 `127.0.0.1` 指向容器，必须允许配置 `baseUrl`。
- Token 放在 iframe URL 查询串会通过 `Referer` 泄漏，嵌入场景应改用 `postMessage` 握手传递，并设置 `Referrer-Policy: no-referrer`。

**操作步骤**

1. 写 `pyproject.toml` 与 `requirements.in`，保证两者依赖一致。
2. 在干净虚拟环境中执行 `pip-compile --universal` 生成锁文件；检查 Windows 专属包带 `sys_platform == "win32"` marker。
3. 编写 bootstrap 脚本，处理解释器不存在、venv 已存在、pip 升级失败等情况，并给出明确错误信息。
4. 修改启动脚本，优先使用项目内 `.venv`，避免 PATH 上的 Python 不一致。
5. 用 `scripts/doctor.py` 做环境自检，并写入 README 的排障步骤。

**验证**

- Windows：删除 `.venv` 后运行 `scripts/bootstrap.ps1`，再运行 `run.bat`，页面和 `/api/all` 正常。
- Linux：在 Ubuntu 22.04/24.04 上运行 `scripts/bootstrap.sh`，再运行 `run.sh`，服务可启动。
- `pip check` 无冲突；`scripts/doctor.py` 能识别当前平台与缺失依赖。
- 锁文件安装不因 `WMI`/`pywin32` 在 Linux 上失败。

**Windows 适配层**

- 将 `is_elevated`、`request_elevation`、`wmi_client`、`collect_disk` 的 WMI 部分、`GpuPerfReader`、`collect_network_detail` 的 WMI 部分、`LhmReader`、`CpuTemperature` 的 Windows 来源整体迁入 `platform/windows.py`。
- 对外暴露统一函数：
  - `is_elevated()`
  - `request_elevation(argv)`
  - `physical_disks()`
  - `network_details()`
  - `temperature_sources()`
  - `integrated_gpu()`
  - `capabilities()`
- 保留现有返回结构和日志文案，减少行为变化。
- Windows 专属的 `CREATE_NO_WINDOW` 提取为 `subprocess_flags()`，Linux 返回空。

**Linux 适配层**

- 权限：`is_elevated()` 用 `os.geteuid() == 0`；`request_elevation()` 直接返回 `False`，启动日志提示「Linux 不自动提权，传感器权限不足时请用 sudo 或加入相应用户组」。
- CPU 温度：
  1. `psutil.sensors_temperatures()`，优先 `Package id 0`、`Tctl`、`Tdie`、`Core 0`，来源 `hwmon`；
  2. 回退 `/sys/class/thermal/thermal_zone*/temp`，按 `type` 选择包含 `x86_pkg_temp`、`cpu`、`soc` 的区域，毫摄氏度转摄氏度，来源 `thermal`；
  3. 都没有时返回 `None`，页面显示 `--`。
- 磁盘：
  - 分区继续用 `psutil.disk_partitions` + `disk_usage`；
  - 物理盘遍历 `/sys/block/*`，排除 `loop*`、`ram*`、`dm-*`、`sr*`、`zram*`，读取 `device/model`、`device/serial`、`size`（512 字节扇区）、`queue/rotational`；
  - 设备名映射：`/dev/nvme0n1p1` → `nvme0n1`，`/dev/sda1` → `sda`；读取失败则跳过。
- 网卡详情：
  - 复用 psutil 的地址、MAC、速率、MTU、up；
  - 网关解析 `/proc/net/route`，DNS 解析 `/etc/resolv.conf`；
  - `dhcp` 无法可靠判断时为 `null`，前端显示「未知」；
  - 不依赖 `ip`/`ifconfig` 命令，避免最小系统缺失。
- GPU：
  - NVIDIA：复用 `NvmlSession` 与 `nvidia-smi`；
  - AMD：读取 `/sys/class/drm/card*/device/gpu_busy_percent`、`mem_info_vram_used`、`mem_info_vram_total`，温度读 `hwmon/hwmon*/temp1_input`，型号从 `uevent`/`lspci` 尽力获取；
  - Intel 核显：基础阶段返回 `None`，页面显示「未检测到核显」；
  - 所有 GPU 数据缺失时保持 `null`，不抛异常。
- 物理盘、网卡详情、温度都按能力表标记 `available`，前端隐藏或降级，不依赖固定平台判断。

**采样调度改造**

- `sampler.py` 从平台模块获取采集器集合，保持现有节奏：
  - 快：CPU、内存、网络速率、GPU、温度；
  - 慢：磁盘、系统信息、核显；
  - 引擎：`nvidia-smi`。
- `state.py` 保持 `put/put_error/collect` 语义，避免改变错误隔离行为。
- `/api/all` 新增 `platform` 字段；`/api/start` 新增 `capabilities`；已有字段不变。

**前端改造**

- `API_BASE` 改为同源优先：
  ```javascript
  const API_BASE = new URLSearchParams(location.search).get('api') || location.origin;
  ```
  仅当 `location.protocol === 'file:'` 时回退到 `http://127.0.0.1:5678`。
- 温度来源标签增加 `hwmon → CPU HWMON`、`thermal → CPU THERMAL`。
- 将 Windows 专属文案改为平台中性：
  - 「任务管理器」→「系统进程管理器」；
  - 「ipconfig」→「网卡详情」；
  - 「Windows GPU 性能计数器」→「系统 GPU 性能计数器」。
- 根据 `platform.capabilities` 控制 iGPU 卡片、GPU 引擎入口、温度来源提示的显示；无能力时展示「当前平台不可用」，不隐藏整个布局。
- 保留现有两个页面结构，暂不合并，避免大范围回归；缩略页使用独立的 `plugin/widget.*`。

**验证**

- Windows 逐项对比改造前后的 `/api/all` 字段、温度来源、GPU 引擎、物理盘、网卡详情。
- Ubuntu 22.04/24.04：
  - `/api/all` 包含 `cpu`、`memory`、`disk`、`network_speed`、`system_info`；
  - 有 `coretemp`/`k10temp` 时 `/api/temperature` 返回 `source: "hwmon"`；
  - 无传感器时返回 503 或 `null`，进程不崩溃；
  - `pytest` 全部通过。
- WSL2：基础指标可用；温度/核显缺失时页面正常降级。

### Phase 3：插件化与对话区缩略集成

**目标**：提供通用嵌入组件；在支持的宿主中把缩略监控放到对话区左上角；提供独立集成页和适配器。

**后端新增**

| 路由/文件 | 说明 |
|---|---|
| `GET /plugin` | 集成中心页面，展示服务状态、平台能力、实时预览、配置生成、适配器说明 |
| `GET /widget` | 缩略监控页，供 iframe 使用；无侧栏、无 Google Fonts |
| `GET /embed.js` | 宿主注入脚本，`Content-Type: application/javascript`，`no-cache` |
| `GET /api/plugin/manifest` | 返回插件名、版本、API 版本、`baseUrl`、`widgetUrl`、`dashboardUrl`、能力表、鉴权方式 |
| `GET /api/start` | 增加 `capabilities` 与 `platform` 字段 |

**安全响应头**

- 所有 HTML：`Referrer-Policy: no-referrer`、`X-Content-Type-Options: nosniff`。
- 完整页面：`Content-Security-Policy: frame-ancestors 'self'`，避免被任意站点嵌入。
- `/widget`：`Content-Security-Policy: frame-ancestors <MONITOR_FRAME_ANCESTORS>`，默认只允许本机来源：
  ```text
  'self' http://127.0.0.1:* http://localhost:*
  ```
  接入 DSH/DeepSeek 时由用户显式追加对应 https 源，例如 `https://chat.deepseek.com`。
- 不使用 `X-Frame-Options`，避免与 `frame-ancestors` 冲突。
- 静态 JS 明确 `Content-Type`，页面和脚本均 `no-cache`。

**缩略组件设计**

`plugin/widget.html` + `widget.css` + `widget-core.js` + `widget.js`：

- 尺寸：展开约 320×180，折叠约 132×36；布局为单列紧凑卡片。
- 指标：CPU、内存、GPU、温度、网络上下行；无数据时显示 `--` 或「不可用」。
- 交互：折叠/展开、拖动、关闭、「打开完整面板」链接；位置和折叠状态存 `localStorage`。
- 主题：`auto | light | dark`；`auto` 跟随 `prefers-color-scheme` 或宿主的 `data-theme`；不使用 Google Fonts。
- 轮询：每 2 秒请求 `/api/all`；页面隐藏时暂停；失败退避 2s→5s→10s，显示离线状态和重试按钮。
- 渲染核心 `widget-core.js` 暴露：
  ```javascript
  window.HardwareMonitorWidget = {
    mount(container, options),
    render(data, options),
    setTheme(theme),
    destroy()
  };
  ```
  该文件同时供 iframe 页面和用户脚本使用，避免重复实现。

`plugin/embed.js`：

- 通过 `<script>` 的 `data-*` 配置：
  - `data-target`：挂载容器选择器；缺省为 `body`；
  - `data-position`：`top-left | top-right | bottom-left | bottom-right`，默认 `top-left`；
  - `data-theme`：`auto | light | dark`；
  - `data-base-url`：服务地址，默认脚本来源的 origin；
  - `data-token`：可选，推荐由宿主配置注入，不写进 URL；
  - `data-collapsed`：初始是否折叠。
- 使用 Shadow DOM 隔离宿主样式；定位优先 `absolute` 挂到 `data-target`，失败回退 `fixed` 视口左上角。
- 通过 iframe 加载 `/widget?embed=1`，`postMessage` 握手：
  1. iframe 发送 `monitor:ready`；
  2. 宿主发送 `monitor:init`，包含 `baseUrl`、`token`、`theme`、`compact`；
  3. 宿主可发送 `monitor:set-theme`、`monitor:refresh`、`monitor:collapse`；
  4. iframe 回传 `monitor:state`，用于宿主状态栏或调试。
- 校验 `event.source === iframe.contentWindow`，并校验 `event.origin` 属于允许列表；不把 token 放进 iframe URL。
- 暴露 `window.HardwareMonitor.mount(options)`、`unmount()`、`toggle()`，便于宿主适配器调用。

`plugin/plugin.html`：

- 服务状态：调用 `/api/start` 显示在线、平台、权限、能力。
- 实时预览：内嵌 `/widget`，支持切换主题、折叠、位置。
- 配置生成：填写目标选择器、位置、主题、base URL、token，生成 `<script>` 片段和 `data-*` 配置。
- 适配器说明：DeepSeek/DSH、Trae/Cursor、Codex 的接入步骤与限制。
- 安全提示：建议 `MONITOR_HOST=127.0.0.1`，不要在公共页面暴露 token。

**宿主适配器**

| 适配器 | 目录 | 实现方式 | 关键限制 |
|---|---|---|---|
| 通用 Web/Electron | `plugin/adapters/web/README.md` | 引入 `/embed.js`，配置 `data-target`；适用于 DSH、DeepSeek Web、Codex Web | 需要宿主 DOM 选择器；HTTPS 页面在 Safari 可能拦截 http iframe |
| 用户脚本 | `plugin/adapters/userscript/hardware-monitor.user.js` | `GM_xmlhttpRequest` 取 `/api/all`，用 `widget-core.js` 在 Shadow DOM 渲染，不使用 iframe | 需要 Tampermonkey 等脚本管理器；token 存脚本配置 |
| VS Code 系扩展 | `plugin/adapters/vscode/` | 扩展宿主轮询 API，状态栏显示 CPU/内存；WebviewView/面板用 `widget-core.js` 渲染；命令打开完整页面 | 不能注入内置聊天 DOM；Trae/Cursor 需验证扩展 API 兼容性；远程场景需配置 `baseUrl` |
| Codex CLI | `plugin/adapters/codex/statusline.py` | 读取 `/api/all`，输出单行 `CPU 12% | MEM 57% | GPU 7% | 58°C` | 需 Codex/终端支持自定义状态行；否则可放在独立终端面板 |
| DSH 专用配置 | `plugins/dsh-hardware-monitor/adapter.config.json` + `inject.js` | 读取配置中的目标选择器、位置、主题，加载 `embed.js` | DSH 的 DOM 结构需实测后填写；无法注入时退回用户脚本或独立窗口 |

VS Code 系扩展详细范围：

- `plugin/adapters/vscode/package.json`：命令 `hardwareMonitor.openDashboard`、`hardwareMonitor.toggleWidget`；配置 `hardwareMonitor.baseUrl`、`token`、`refreshInterval`；状态栏项；WebviewView 容器。

## 5. 关键设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 虚拟环境工具 | 标准 `venv` + `pip-compile --universal` | 不引入额外运行时依赖；锁文件可跨 Windows/Linux，平台包用 marker 区分 |
| Python 基线 | 3.10，兼容 3.11/3.12 | 与现有 README 一致；bootstrap 允许更高版本并提示 |
| 重构方式 | 渐进式迁移，保留 `server.py` 入口和现有 URL | 降低 Windows 回归风险，用户启动习惯不变 |
| 平台抽象 | 共享 psutil 采集 + `platform/windows.py` / `platform/linux.py` | Windows 专有代码集中，Linux 只实现基础能力 |
| Linux 范围 | 基础指标完整，温度/GPU/物理盘型号尽力而为 | 符合用户选择，避免为每种发行版做深度驱动适配 |
| 插件核心 | 纯 JS，`widget-core.js` 同时供 iframe 和用户脚本使用 | 无构建、易分发、避免两套渲染逻辑 |
| 宿主适配 | 通用嵌入优先，VS Code 扩展和用户脚本作为薄适配器 | 用户选择通用组件；不同平台能力差异大 |
| 缩略位置 | 默认对话区左上角，可配置目标容器和四角位置 | 满足「对话框内左上角」需求，同时兼容不同 DOM |
| Token 传递 | `postMessage` 握手，不放入 iframe URL | 避免 `Referer` 泄漏；完整页面查询参数仅保留兼容 |
| 嵌入安全 | `/widget` 使用 `frame-ancestors` 白名单，默认仅本机 | 防止任意网站嵌入；接入外部宿主时显式配置 |
| HTTPS 页面 | 用户脚本/扩展取数并渲染，不依赖 http iframe | 规避 Safari/iOS 混合内容限制；Chrome loopback 豁免不作为唯一方案 |
| VS Code 系 | 侧边栏/面板/状态栏，不承诺注入聊天 DOM | 平台没有公开的聊天 DOM 注入 API，避免交付不可实现的承诺 |
| 无数据时 | 统一 `null`/503 + 前端「不可用」 | 与现有 `/api/all`、`/api/<key>` 语义一致 |

## 7. 风险与回退

| 风险 | 影响 | 缓解 |
|---|---|---|
| Windows WMI/PDH 迁移引入回归 | 温度、核显、物理盘异常 | 先整体搬迁、保持函数签名；逐项对比 `/api/all`；保留旧 `server.py` 可回退 |
| Linux 硬件差异大 | 温度/GPU 数据不稳定 | 能力表 + 多级回退 + `null`；基础指标优先 |
| HTTPS 页面嵌入 http 服务 | Safari/iOS 混合内容拦截 | 用户脚本/扩展直接取数渲染；文档明确限制 |
| VS Code 系无法注入聊天 DOM | 无法实现「聊天框左上角」 | 提供侧边栏/面板/状态栏，明确平台限制 |
| Token 通过 URL 泄漏 | 本机 token 暴露 | 嵌入默认走 `postMessage`；设置 `Referrer-Policy: no-referrer` |
| `frame-ancestors` 配置错误 | 组件被拒绝嵌入或过度开放 | 默认仅本机；提供 `/plugin` 配置生成与文档 |
| 依赖锁文件跨平台不完整 | Linux 安装失败 | `pip-compile --universal` + 平台 marker；Windows/Linux 分别跑安装验证 |
| 扩展构建引入 Node 工具链 | 用户环境复杂 | 扩展为可选适配器；核心插件纯 JS，无构建即可用 |
| 端口冲突/远程开发 | 地址不可达 | `baseUrl`、`MONITOR_PORT` 可配置；`/plugin` 显示当前地址 |

## 8. 交付顺序与完成标准

### M1：可复制环境

交付：`pyproject.toml`、`requirements.in/txt`、bootstrap 脚本、`run.sh`、`server.py` 兼容入口保持可用、doctor 脚本、README 更新。

完成标准：Windows 与 Ubuntu 都能从零创建 `.venv`、启动服务并访问 `/api/all`。

### M2：跨平台采集

交付：`hardware_monitor/` 包、Windows/Linux 平台模块、能力表、`/api/all` 的 `platform` 字段、Linux 基础指标、前端能力降级、测试。

完成标准：Windows 功能不回退；Ubuntu 基础指标稳定；无平台相关 traceback。

### M3：插件与缩略集成

交付：`/plugin`、`/widget`、`/embed.js`、`/api/plugin/manifest`、`widget-core.js`、通用嵌入脚本、用户脚本、VS Code 系扩展骨架、Codex 状态行脚本、DSH 配置模板、安全头。

完成标准：本地 HTTP 页和 HTTPS 用户脚本场景都能显示左上角缩略监控；VS Code 系可通过扩展面板查看；集成页可生成配置。

### M4：测试、文档与发布

交付：自动化测试、完整文档、插件 README、源码发布包；可选 CI。

完成标准：`pytest` 通过；文档覆盖 Windows/Linux/插件接入；新用户按文档完成安装并能在页面看到数据。

## 9. 计划审查清单

评审本文时按以下问题逐项确认；未通过的项目回到对应章节修订，不进入实施。

### 9.1 范围与优先级

- [ ] Must/Should/Could 划分是否符合当前资源与目标？
- [ ] 是否接受「Linux 基础指标优先」而不是一次对齐 Windows 全部能力？
- [ ] 是否接受「VS Code 系不注入内置聊天 DOM」这一平台限制？
- [ ] 是否有必须提前的适配器（例如 DSH 必须首期支持）？

### 9.2 可复制环境

- [ ] Python 基线 3.10、兼容 3.11/3.12 是否可接受？
- [ ] `venv` + `pip-compile --universal` 是否满足团队习惯，还是需要 `uv`/Poetry？
- [ ] 锁文件是否提交到仓库？Windows/Linux 是否都需要独立验证？
- [ ] `run.bat` 保留 `py -3.10` 回退是否必要？

### 9.3 跨平台

- [ ] Windows 现有的 WMI/PDH/LHM 功能是否有明确的不回退清单？
- [ ] Linux 的「基础指标」定义是否认可（CPU/内存/分区/网络速率/进程/系统信息）？
- [ ] 温度来源 `hwmon`/`thermal` 的标签与降级文案是否可接受？
- [ ] 无核显/无 NVIDIA 时，iGPU/GPU 卡片是隐藏还是显示「不可用」？

### 9.4 插件与安全

- [ ] 通用嵌入组件 + 薄适配器的路线是否认可？
- [ ] 缩略窗的尺寸、位置、折叠/拖动交互是否符合预期？
- [ ] Token 通过 `postMessage` 传递、iframe URL 不带 token 是否可接受？
- [ ] `frame-ancestors` 默认仅本机、外部宿主需显式配置是否可接受？
- [ ] HTTPS 页面使用用户脚本/扩展取数渲染，是否接受这一限制？
- [ ] 插件是否需要支持局域网多机查看，还是只面向本机？

### 9.5 交付与验收

- [ ] M1-M4 的交付物是否完整、可独立验收？
- [ ] 验收矩阵是否覆盖目标设备与宿主？
- [ ] 文档更新范围（README、使用说明、Code Wiki）是否足够？
- [ ] 是否需要 CI、VSIX 打包或发布签名？
